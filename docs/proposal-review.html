Steady Ride 기획서 검토

팀원이 작성한 「Steady Ride 동승자 멀미 저감 주행 보조 앱」 기획서를 심사 기준 4개로 평가하고, 기획서의 SDK 가정을 Pleos 공식 문서와 실제 Pleos Connect 에뮬레이터(v2.1.0, API 34)에서 확인한 결과와 대조했습니다.

작성 2026-11-081차 접수 마감 2026-11-15 (D-7)근거: document.pleos.ai · Vehicle SDK 2.3.2 · 에뮬레이터 실측
총평

문제 정의와 해결 가설은 탄탄하고 바로 쓸 수 있는 수준입니다. 다만 기술 근거와 차량특화성 표에 실제와 다른 가정이 섞여 있어, 지금 상태로는 심사위원이 가장 먼저 짚을 곳이 바로 거기입니다.

  • 살릴 것 — "운전자는 다음 움직임을 알기 때문에 멀미하지 않는다"에서 예측 큐(M1)를 끌어낸 논리, 주행/정차/주차 모드 분리, 운전석 무텍스트 원칙, MAU 계산식 구조.
  • 고칠 것 — 횡가속도·요레이트·경로 곡률은 Pleos SDK에서 제공되지 않거나 확인되지 않았습니다. 반대로 기획서가 "불확실"로 둔 공조·시트 통풍·앰비언트 쓰기 API는 실제로 있습니다. 모듈 우선순위를 뒤집어야 합니다.
  • 새로 대비할 것 — 스마트폰에서 주변시 점으로 멀미를 줄이는 기능은 이미 출시돼 있습니다(Apple iOS 18 「차량 모션 큐」). "스마트폰으로는 불가능"이라는 주장은 그대로 두면 반박당합니다.
심사 기준별 평가

현재 기획서 vs 수정 후 예상

5점 척도, 검토자의 주관적 추정입니다. 회색 막대가 현재, 청록 막대가 아래 수정 사항을 반영했을 때입니다. 실제 배점은 공개되지 않았습니다.

차량특화성 현재 3.0 → 수정 후 4.5

방향은 맞지만 근거 표에 틀린 행이 있습니다. 조향각 선행성, 좌석 점유, 공조·조명 제어로 근거를 바꾸면 가장 강한 항목이 됩니다.

창의성 현재 3.5 → 수정 후 4.0

Pain Point 정의는 우수합니다. 선행 사례를 먼저 인정하고 "반응형이 아니라 예측형 + 차량 액추에이터"로 차별점을 좁히면 오히려 신뢰도가 오릅니다.

기술 활용성 현재 2.0 → 수정 후 4.0

06장이 전부 가정이고 API 이름이 없습니다. 실제 메서드명으로 교체하고 에뮬레이터 동작 영상을 붙이면 점수 차이가 가장 큰 항목입니다.

사업성 현재 3.0 → 수정 후 3.5

계산식 구조는 좋지만 계수 4개가 모두 근거 없는 가정입니다. 설문 N≥30과 A값 출처만 채워도 충분합니다.

수정 사항

우선순위 순으로 고칠 것

필수

차량특화성 표의 틀린 행 교체

04장

"차체 횡가속도·요레이트 — 스마트폰은 간접 추정만 가능, 차량은 정밀값"은 사실과 반대입니다. Pleos에는 이 값이 없고, 앱도 결국 기기 센서를 씁니다. "전방 경로 곡률"도 근거가 없습니다.

바꿀 근거: ① 조향각은 차체가 실제로 돌기 전에 바뀐다 — 폰 센서는 이미 일어난 움직임만 안다 ② 좌석별 점유로 누가 어디 탔는지 안다 ③ 공조·시트 통풍·앰비언트 조명을 직접 움직인다 ④ 주행/정차 상태로 운전석 UI를 자동 제한한다.

필수

선행 사례를 인정하고 차별점을 좁히기

01·04장

"20년간 아무도 소프트웨어로 풀지 않았다", "스마트폰으로는 구현 자체가 불가능"은 Apple iOS 18의 「차량 모션 큐」(화면 가장자리 점으로 차량 움직임 표시)로 바로 반박됩니다.

바꿀 포지션: "폰은 이미 일어난 움직임에 반응한다. Steady Ride는 차량 조향 신호로 움직임을 먼저 알리고, 폰을 쥐지 않은 아이에게도 조명과 공조로 작동한다." 선행 사례를 먼저 꺼내면 원리 검증 근거로도 쓸 수 있습니다.

필수

06장 SDK 매핑표를 실제 API 이름으로 교체

06장

현재는 "API 명칭은 문서 확인 후 확정" 상태입니다. 기술 활용성은 "Pleos SDK를 핵심 기능에 적절히 썼는가"를 보므로 메서드명과 권한이 적혀 있어야 합니다.

바꿀 내용: 위 사실 확인 표의 "실제 제공 방식" 열을 그대로 옮기고, Pleos SDK / 표준 Car API / 기기 센서를 구분해 표기합니다.

권장

"2~4초 선행 예측"의 근거를 내비 TBT로 교체

02·03장

곡률 데이터는 없지만, 내비 경로 주행 중에는 NaviHelper가 다음 회전 종류와 남은 거리를 줍니다. 남은 거리 ÷ 차속으로 회전까지의 시간을 계산하면 2~4초 예고가 가능합니다. 경로 안내가 없을 때는 조향각이 유일한 선행 신호라 예고 시간이 짧습니다.

바꿀 표현: "내비 경로 주행 시 회전 2~4초 전 예고(TBT 거리 ÷ 차속), 경로 없이 달릴 때는 조향 입력 즉시 예고"로 두 단계를 나눠 적습니다.

권장

모듈 우선순위 재배치

03·08장

기획서는 M2(공조)를 "권한 불확실 → 선택"으로 두었지만 쓰기 API가 모두 있습니다. M4는 곡률 기반 자체 경로 계산은 불가능하지만, 내비에 COMFORTABLE(편안한 경로) 옵션이 이미 있어 훨씬 가볍게 구현됩니다.

바꿀 순서: M1 예측 큐 + M2 환경 개입(핵심으로 승격) → M3 코칭 → M4는 "아이 동승 시 편안한 경로로 재탐색 제안"(NaviHelper 경로 옵션 변경) 정도로 축소. M2는 에뮬레이터에서 바로 시연되므로 1차 영상의 임팩트가 커집니다.

권장

출력 표면을 단일 화면 + 앰비언트로 재정의

03·05장

"기존 콘텐츠 위 오버레이"와 "앰비언트 라이트 좌·우로 흘리기"는 확인되지 않았거나 심사상 위험합니다. 또 Pleos UI 가이드는 운전 중 운전자 시선을 끄는 애니메이션을 금지하므로, 움직이는 광학 흐름을 운전자가 보는 화면에 띄우면 M1 자체가 규정에 걸릴 수 있습니다. 한편 와이드 디스플레이(Connect-W)는 조수석에서 실행한 앱을 조수석 쪽 창에만 띄웁니다.

바꿀 설계: 움직이는 큐는 조수석 창(Connect-W) 또는 정차 중으로 한정하고, 일반 디스플레이에서 주행 중에는 정적 방향 표시 + 앰비언트 밝기·색 신호만 씁니다. 이 구분을 기획서에 명시하면 운전자 주의 분산 질문에 대한 답이 됩니다.

참고

예시 수치를 사실처럼 보이지 않게

03장 M3

"뒷좌석 멀미의 62%는 정체 구간 가감속에서 발생"은 출처 없는 예시인데 통계처럼 읽힙니다.

바꿀 표현: "예: ○○ 구간 가감속이 이번 주행 멀미 유발 점수의 대부분을 차지" 처럼 앱 화면 예시임을 명시합니다.

참고

사업성 계수 근거 채우기

07장

계산식 구조는 좋습니다. 남은 것은 A(탑재 차량 수) 출처와 B·C·D 근거입니다.

할 일: 간이 설문 N≥30(동승 멀미 경험률, 현재 대처법, 사용 의향)으로 C·D를 채우고, A는 Pleos 탑재 계획 공개 자료나 신차 등록 통계로 범위를 잡습니다.

분석

강점과 리스크

그대로 살릴 강점

  • 감각 불일치 → 예측 가능성 → 주변시 큐로 이어지는 원인-해법 논리.
  • 운전자와 동승자 경험이 구조적으로 분리돼 있다는 문제 정의. 심사의 "Pain Point 정의" 항목에 정확히 맞습니다.
  • 주행 중 운전석 무텍스트, 코칭은 정차 후. Pleos 앱 심사의 운전 주의 분산 기준과도 맞습니다.
  • /core 순수 로직 분리와 /replay 로그 재생 하네스. 차속을 콘솔로 넣을 수 없어서 재생 하네스는 이제 필수입니다.
  • 90초 시연 영상 구성. 특히 "커브 진입 전 큐가 먼저 반응하는 장면"을 핵심으로 잡은 판단.

남은 리스크

  • 효과 입증 — 소규모라도 A/B 수치가 없으면 PT에서 막힙니다. 1차에는 선행 연구 인용, PT 전까지 간이 측정.
  • 표준 API 사용 허용 여부 — 차속·센서를 Pleos 밖에서 가져오는 것이 심사에 불리한지 운영사 확인 필요.
  • 쓰기 권한 승인 — 공조·조명 제어는 실제 출시 시 App Market 승인 대상. 기획서에 필요 권한과 사유를 명시해 두면 리스크가 설계 역량으로 읽힙니다.
  • 일정 — 1차 마감까지 7일. M1 + M2 간단 버전을 넘기면 영상 품질이 떨어집니다.
